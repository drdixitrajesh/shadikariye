# ManageLove on Sudama

Live website: https://managelove.com

Hosting: Sudama Dokploy, project `ManageLove`, application `ManageLove Sudama` (`AKe0fBSobpaNyG3b4j1AJ`). Dockerfile: `Dockerfile.sudama`. Build uses pinned Node 24.19.0 and pnpm 11.25.0, with the existing Vinext app and native SQLite. One replica only; multiple replicas must not share this SQLite volume.

## Storage and routing

Persistent Docker volume `managelove-sudama-data` is mounted at `/data`; database is `/data/managelove.sqlite`. Accounts, sessions, profiles and private photos are stored here. Deploying or restarting the app must preserve this volume. Do not delete the volume or deploy an empty replacement database.

Cloudflare Tunnel `dokploy-sudama` (`d5cd04ad-9a55-45c6-ba23-5814b56c9115`) routes the apex, www and staging hostname to `http://localhost:80`. Traefik routes these hostnames to application port 3000; no application host ports are published. Cloudflare supplies public TLS. `VINEXT_TRUST_PROXY=1` and `TRUST_CLOUDFLARE_PROXY=1` are required for this topology. Only enable these settings when the application's origin is reachable through the trusted tunnel.

Runtime secrets live in Dokploy, never in Git or build arguments. Preserve `PORTAL_KEY` for the lifetime of the database; changing it after MFA enrollment makes existing encrypted MFA secrets unreadable. Keep the production Turnstile credentials and the canonical hostname `managelove.com`.

Public posting is enabled with `PUBLIC_REGISTRATION=1`. `/register` creates a normal member account after terms acceptance, password validation and Turnstile; signup directs the member to the existing profile editor. Publishing still requires profile details, reference consent and publication consent. Members are not labelled phone/identity verified. Original invited test accounts remain fictional and administrator accounts retain mandatory MFA. Setting the flag to `0` closes signup and removes publishing access for public accounts while retaining original test access.

New posts and content/photo edits wait for admin approval. In `/admin`, select “केवल approval बाकी”, open a member, review all details/photos, then use Approve or Reject with a reason. Rejection reasons appear to the member in their profile editor. Review decisions require an MFA admin session, same-origin request and the current review token; content/photo changes invalidate stale reviews. Decisions are stored in `admin_actions`. Existing posts without an approval field retain their prior published status until edited; no database schema migration or bulk approval is performed. Review does not change public-listing consent or renew expiry.

Photo protection: Node startup supplies `PHOTO_PROTECTION` using pinned Sharp. Authorized `/api/photo/<key>` responses (including owner/admin and raw/download query attempts) are JPEGs with repeated vector-lettered Vedik Milan/private marks and a secret-derived opaque viewer code, limited to 900 × 1100 pixels without enlargement. Original SQLite bytes remain private and unchanged. Responses retain private/no-store and have `X-Photo-Protection: watermark-v1`; rendering failure is closed (503). Two concurrent renders and a 12-item waiting queue bound processing; a 16 MiB/64-entry LRU stores only protected results. No watermark removal/original-download switch is available to members. Browser guards discourage right-click, drag and selection around photos/profile panels; print CSS hides profile images. This deters routine copying, but cannot prevent screenshots, cameras, devtools or removal/reconstruction by a determined viewer. These controls do not authorize sharing others' photos.

Forgot password: `/forgot-password` and POST `/api/portal/recover` are available before login/mobile setup. Requests never disable an account or revoke its session; known/unknown accounts receive the same generic 202 response. Turnstile action is `recover`. Three per-account attempts (username/mobile aliases combined), plus IP/global limits, protect the private queue. Under `/admin?section=help`, MFA administrators view pending requests and stored contacts. Independently verify the holder through stored contact details, select the request, check the identity confirmation, supply a reason, and issue a private 30-minute single-use link. Share it manually with the verified holder. No automated SMS/email is sent. Issuing a link invalidates the old password/sessions and clears that account's login lock; activation consumes the hashed token and sets the new password. Anonymous requests cannot recover admin/disabled accounts. Native migration creates `portal_recovery_requests`; D1 migration is 0008. Admin recovery still requires the separate verified operator process.

Public browsing and attempt limits (21 October 2026): native startup keeps `REQUIRE_ACCOUNT_MOBILE=1` for member features and administration. GET/HEAD home, public state and photo requests are allowed before sign-in; state and photos independently enforce approved, opted-in, unexpired, non-test visibility. Accounts without a stored mobile receive the same public projection, never their private member/admin state. Public photos use a secret-derived public watermark tag and never return originals; render failures stay closed. The native image optimizer remains disabled. Private profiles remain member-only, public consent is visible in the editor, and no existing profile consent or approval is rewritten. Three failed password or MFA attempts lock the corresponding check for 15 minutes across aliases and sessions. Atomic reservation enforces the limit; success resets it. ## Recovery

The pre-migration Cloudflare Worker `managelove` and D1 database `managelove-test-portal` were retained. Builds and the public Workers URL are disabled, and `managelove.com/*` / `www.managelove.com/*` no longer invoke the Worker. Merely restoring those routes after new server writes would discard the new writes from the user's view. Freeze writes and reconcile the current SQLite data before reverting to D1.

Before migration, apex DNS was two proxied A records (`3.33.152.147`, `15.197.142.173`); www was a proxied CNAME to `managelove.com`. Apex now points to the Sudama tunnel CNAME; www resolves to that tunnel as well.

Initial snapshot: 7 accounts, 6 profiles, zero enrolled MFA secrets; SHA-256 `5d853705d0f6cf2193199c22a6c93e1e152f0a5255706a7f09c29df0b3a014a3`. DPAPI backups require that same Windows account. Retain protected copies of database and MFA key together. This migration does not configure automatic off-server backups.

Dokploy MCP is installed locally with protected credentials. Its Access policy is restricted to the Sudama Dokploy panel. The temporary D1/Turnstile read token used for export was revoked after verification.

## Member administration
After administrator MFA, /admin shows real members and publication status. Enable the test-account checkbox to include fictional seed accounts. Each member links to /admin/members/<account-id> for the public-profile preview, photos, current account/publication dates and retained activity counts/timeline. GET /api/admin/members enforces administrator MFA and paginates the list. Counts describe retained records; this is not a complete historical click or login audit. Private references, identity details, credentials and message bodies are excluded. Authenticated administrators can preview member photos without consuming member browsing quotas. Password setup is in the separate login-help section; deletion remains behind name/reason confirmation. No schema migration is required.

Public visibility is per profile and defaults off. Authenticated members may opt in with the subject's consent or turn it off in the profile editor. Anonymous /api/state exposes only opted-in, unexpired, non-test profiles (all matching posts), excludes contact email and all private identity/reference data, and exposes protected versions of their current photos. Photo access rechecks live visibility and uses no-store responses. Other profiles remain member-only. Administrator member screens show the audience explicitly. Changing visibility does not reset publication or expiry timestamps.
